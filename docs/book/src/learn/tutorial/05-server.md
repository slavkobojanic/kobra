# 5. Save books on the server

In this step you'll save each book you add in a database on the server, so it outlasts the browser tab.
You'll describe the table, write a migration that creates it, declare what the browser may ask the server
to do, and answer that on the server.

Start from the project you finished in [step 4](04-style.md), with `k dev` running. The finished step is in
the repository as `examples/learn/shelf/05-server`.

## Describe the table

So far the app has run in the browser; the server only sent the first page. Now the server keeps the
books. An `entity` declares a table of the database: each field is a column. Create
`src/books/BookRecord.k`:

```k
// examples/learn/shelf/05-server/src/books/BookRecord.k
import k.crypto.Uuid
import k.db.Id

/// A book as the server stores it: one row of the `book_record` table.
public entity BookRecord {
    /// The primary key, a random id the server picks when the book is added.
    @Id let id: Uuid
    /// The book's title.
    var title: String
    /// Who wrote it.
    var author: String
    /// When the book was added, which orders the list.
    let addedAt: Date
}
```

- The table is named after the entity, `book_record`, and each column after its field: `addedAt` is
  `added_at`.
- `@Id` marks the primary key, the column that tells rows apart. A `Uuid` is a random id, so the server
  can pick a new one without asking the database which numbers are taken.
- It's a `BookRecord`, not a `Book`: `Book` stays what the browser shows. Entities exist only on the
  server, and the compiler keeps them out of the browser's code.

In development, `k dev` keeps the database in a file, `.k/shelf.db`, which `.gitignore` already leaves
out. The table doesn't exist in it yet: a migration creates it. Run this in your second terminal:

```console
$ k migrate new "create book records"
wrote migrations/0001_create_book_records.k
wrote schema.lock
```

`k migrate new` compares the entities with `schema.lock`, the record of the tables the migrations
create, and writes a migration for the difference:

```k
// examples/learn/shelf/05-server/migrations/0001_create_book_records.k
// Generated by `k migrate new "create book records"` from the difference between
// the entities and schema.lock. Review it before committing.

/// Create book records.
migration CreateBookRecords {
    func up(schema: Schema) {
        schema.createTable(name: "book_record") { table =>
            table.column(name: "id", type: .uuid).primaryKey(true)
            table.column(name: "title", type: .text)
            table.column(name: "author", type: .text)
            table.column(name: "added_at", type: .timestamp)
        }
    }
}
```

The `k dev` terminal shows `applied migration 0001_create_book_records` as it restarts: the table now
exists. Commit the migration and `schema.lock` with your code, and every other copy of the app, a
teammate's or the one in production, creates the same table.

## Read and write the table

A `repository` is the server's code for one table. Create `src/books/BookRepository.k`:

```k
// examples/learn/shelf/05-server/src/books/BookRepository.k
/// The `book_record` table, for the server's code.
public repository BookRepository for BookRecord {
    /// Returns every book on the shelf, the first one added first.
    func all() async -> List<BookRecord> {
        return await bookRecords.sortedBy { record => record.addedAt }
    }
}
```

- Every repository can already `insert`, `update` and `delete` a row. `all()` is a query of your own.
- Inside it, `bookRecords` is the table, and you query it as you would a `List`. The compiler turns
  `sortedBy { … }` into SQL: `ORDER BY added_at`.
- `{ record => record.addedAt }` is a lambda, a small function written in place: given a record, it
  returns when it was added.
- `async` marks a function that waits for something, here the database, and `await` is where it waits.

## Say what the browser may ask

The browser and the server are two programs. A `protocol` is the contract between them: the functions the
browser may call on the server, each an `rpc` (a remote procedure call). Create `src/books/BookProtocol.k`:

```k
// examples/learn/shelf/05-server/src/books/BookProtocol.k
import k.rpc.RpcOnlyError

/// What the browser can ask the server to do with books.
public protocol BookProtocol {
    /// Saves a book on the shelf. The draft's rules are checked again on the
    /// server before this runs.
    ///
    /// - Returns: the saved book, with the id the server gave it.
    rpc add(draft: BookDraft) throws RpcOnlyError -> Book
}
```

- `add` takes a `BookDraft` and returns a `Book`. `throws RpcOnlyError` says how it can fail: a call over
  the network can always fail, and `RpcOnlyError` is the error for an rpc that has no failures of its
  own.
- The draft is checked against its rules on the server too, before `add` runs, so a request that skips
  the form can't save a book without a title.

What crosses the network must be `Codable`: Kobra can turn it into bytes and back. Add `Codable` to
`BookDraft`:

```k
// examples/learn/shelf/05-server/src/books/BookDraft.k
// ...
public struct BookDraft implements Codable, Validatable {
// ...
```

and to `Book`, whose `id` is now the server's `Uuid`:

```k
// examples/learn/shelf/05-server/src/books/Book.k
import k.crypto.Uuid

/// A book on the reading list, as the server sends it to the browser.
public struct Book implements Codable {
    /// Tells the books apart, even two with the same title.
    let id: Uuid
// ...
}
```

## Answer on the server

A service that `implements` a protocol is the server's side of it. Create `src/books/BookApi.k`:

```k
// examples/learn/shelf/05-server/src/books/BookApi.k
import k.crypto.Uuid
import k.rpc.RpcOnlyError
import k.time.Clock

/// The server's side of `BookProtocol`.
public service BookApi implements BookProtocol {
    @Inject let records: BookRepository
    @Inject let clock: Clock

    rpc add(draft: BookDraft) async throws RpcOnlyError -> Book {
        let record = BookRecord(
            id: Uuid.random(),
            title: draft.title,
            author: draft.author,
            addedAt: clock.now
        )

        await records.insert(record)

        return Book(id: record.id, title: record.title, author: record.author)
    }
}
```

- `@Inject let records: BookRepository` asks Kobra for the repository. You never create services yourself:
  Kobra makes one of each and passes it to whatever injects it.
- `Clock` tells the time. Taking it from Kobra, instead of reading the computer's clock, lets a test set the
  time.
- `add` makes a record, inserts it, and returns the `Book` the browser will show. The compiler checks that
  `BookApi` answers every rpc of the protocol, with the same types.

## Call it from the browser

In the browser, only a service can call a protocol, and components use that service. Create
`src/books/BookService.k`:

```k
// examples/learn/shelf/05-server/src/books/BookService.k
import k.rpc.RpcOnlyError

/// The browser's way to the books on the server. Components use this
/// service; only a service can call a protocol.
public service BookService {
    @Inject let api: BookProtocol

    /// Saves a book on the server.
    ///
    /// - Returns: the saved book.
    /// - Throws: `RpcOnlyError.rpcFailure` when the server can't be reached.
    func add(draft: BookDraft) async throws RpcOnlyError -> Book {
        return try await api.add(draft: draft)
    }
}
```

`@Inject let api: BookProtocol` gets a client that sends each call to the server. You don't write a URL
or a request: calling `api.add` is the request. `try` marks a call that can fail.

The form now saves the book before it reports it. In `src/books/AddBookForm.k`:

```k
// examples/learn/shelf/05-server/src/books/AddBookForm.k
import k.validation.Form

/// A form for adding a book to the shelf. It checks what was typed, saves a
/// book that passes the checks on the server, reports it with `added`, and
/// then clears its fields for the next one.
public component AddBookForm {
    @Inject let books: BookService
    @Form var draft: BookDraft = .empty
    @State var problem: String? = nil

    /// Fired with the saved book, once the server has stored it.
    @Emits let added: Event<Book>

    func submit() async {
        problem = nil

        do {
            let book = try await books.add(draft: draft.value)

            added.emit(book)
            draft.reset()
        } catch .rpcFailure {
            problem = "Couldn't save the book. Check your connection and try again."
        }
    }

    view {
        form {
// ...
            if let problem {
                paragraph { problem }
                    .role(.alert)
            }

            button { "Add book" }
// ...
```

- `do { … } catch .rpcFailure { … }` runs the code in `do`, and if a call in it fails, the code in
  `catch`. An error is an enum, and `catch` names the case it handles; `RpcOnlyError` has only
  `rpcFailure`.
- `String?` is an optional: a `String`, or `nil` for none. `if let problem { … }` shows the message only
  when there is one, and `.role(.alert)` has screen readers announce it.
- `added` now carries the saved `Book`, with the server's id.

The page no longer makes books itself. It starts with an empty list and adds what the form reports. In
`src/home/Home.k`:

```k
// examples/learn/shelf/05-server/src/home/Home.k
import books.AddBookForm
import books.Book
import books.BookRow

/// The app's start page: the reading list.
public page Home at "/" {
    @State var books: List<Book> = []

    func add(book: Book) {
        books.append(book)
    }
// ...
```

The three books from step 2 are gone: the list shows what you add. Add a book in the browser: it joins the
list as before, and it's also a row of the database now. The page doesn't read the books back yet, so a
reload shows an empty list again. Step 6 fixes that.

## Check it

In a test, the browser's calls go to `BookApi` in the same process, with a fresh, empty database for every
test. Clicking Add book now waits for the server, so the tests wait too. Replace `src/home/Home.test.k`:

```k
// examples/learn/shelf/05-server/src/home/Home.test.k
import books.BookRepository
import k.test.render

test Home {
    @Inject let records: BookRepository
// ...
    test "a book added with the form joins the list" {
        let screen = render(Home())

        screen.textField(labeled: "Title").fill("Piranesi")
        screen.textField(labeled: "Author").fill("Susanna Clarke")
        screen.button(named: "Add book").click()
        await screen.settle()
// ...
    }

    test "a book added with the form is saved on the server" {
        let screen = render(Home())

        screen.textField(labeled: "Title").fill("Piranesi")
        screen.textField(labeled: "Author").fill("Susanna Clarke")
        screen.button(named: "Add book").click()
        await screen.settle()

        let saved = await records.all()

        expect saved.count == 1
        expect saved[0].title == "Piranesi"
    }

    test "a book needs a title" {
// ...
        screen.button(named: "Add book").click()
        await screen.settle()

        expect screen.text("Enter the book's title").isVisible
        expect screen.items().count == 0
    }
}
```

- `await screen.settle()` waits until nothing the page started is still running, here the call to the
  server.
- `@Inject let records: BookRepository` gives the test the server's repository, so it can check what was
  saved.

```console
$ k check
checked 14 files, ran 4 tests: no problems
```

## Recap

In this step you:

- declared a table with an `entity`, and created it with a migration from `k migrate new`;
- queried the table in a `repository`, with collection code the compiler turns into SQL;
- declared what the browser may ask in a `protocol` of `rpc`s, and answered it in a service that
  `implements` it;
- called the server from a browser service with `try await`, and handled a failed call with `do` and
  `catch`;
- checked in a test that the book reached the database.
