# Proposal: Migrations and the `schema.lock` Format

> **Status: proposal.** Not yet accepted into the design. First used by `examples/notes`, and consistent with the migrations in `examples/shop`.

## Problem

[19-persistence.md](../19-persistence.md) says `schema.lock` records the current schema and `k migrate new` "generates a reviewable migration from the difference between the entities and the lock", with `@Breaking("reason")` for destructive changes. It doesn't say what a migration file looks like, where it lives, how entity names map to tables and columns, or what the lock contains.

## Proposal

### Naming: entities to tables

- **A table is named after its entity, in snake case:** `entity Note` → `note`, `entity OrderLine` → `order_line`.
- **A column is named after its field, in snake case:** `isPinned` → `is_pinned`.
- **A to-one `@Relation` field stores a foreign key** named after the field with `_id`: `@Relation let note: Note` → `note_id`, referencing `note.id`. Foreign-key columns are indexed automatically.
- **A to-many `@Relation` field** (`@Relation var tags: List<Tag>`) has no column. It is the other side of exactly one to-one relation in the target entity (`Tag.note`); none, or more than one, is a compile error asking for `@Relation(inverse: …)`.
- **`@Index` on a field** adds a single-column index. Multi-column indexes are written in a migration.
- A repository's collection keeps the entity's plural, lower camel case name (`notes`, as in [19-persistence.md](../19-persistence.md)). Only the database uses snake case.

### Migration files

Migrations live in **`migrations/`** at the project root, one per file, named `NNNN_description.k`. Each file holds one `migration` declaration:

```k
// Generated by `k migrate new "add note pinning"`, then reviewed.

/// Adds pinning. Existing notes start unpinned.
migration AddNotePinning {
    func up(schema: Schema) {
        schema.alterTable(name: "note") { table =>
            table.addColumn(name: "is_pinned", type: .boolean)
                .defaultValue(.boolean(false))
        }
    }
}
```

- **`migration` is a declaration keyword,** because a migration has its own compiler semantics: migrations are ordered by file number, replayed in that order, and checked against `schema.lock`.
- **`migrations/` is not a module.** Migration files can't import anything, and nothing can import them.
- **Migrations name tables and columns as strings, not as entity references.** A migration is a record of history: it must keep meaning what it meant after `Note` is renamed or `isPinned` is removed. Every name is still checked, by replaying the migrations, so a typo is a compile error.
- **There is no `down`.** Rolling back production schemas is rarely safe; a mistake is fixed by a new migration.
- **Each migration runs in one transaction** on databases that support transactional DDL (Postgres and SQLite both do).
- `k migrate new "description"` writes the next file from the difference between the entities and `schema.lock`, and updates the lock. `k migrate new --empty "description"` writes an empty migration for data changes (`schema.insert(into:rows:)`, `schema.execute(…)`).
- **The server applies pending migrations at startup,** before it accepts requests. `k test` applies them to each test run's fresh database.

### The `Schema` builder

| Call | Meaning |
|---|---|
| `schema.createTable(name:) { table => … }` | creates a table; columns with `table.column(name:type:)` |
| `schema.alterTable(name:) { table => … }` | changes a table: `addColumn(name:type:)`, `renameColumn(from:to:)`, `dropColumn(name:)` |
| `schema.dropTable(name:)` | drops a table |
| `schema.createIndex(table:columns:)` | adds an index over one or more columns |
| `schema.insert(into:rows:)` | inserts data rows, each a `Map<String, ColumnValue>` |

- **Column options are chained**, following the named-or-chained rule: `.primaryKey()`, `.unique()`, `.nullable()`, `.indexed()`, `.references(table:)`, `.defaultValue(…)`.
- **Column types** are a closed enum mapped per database: `.uuid`, `.text`, `.integer`, `.decimal`, `.boolean`, `.timestamp`, `.money`, `.json`.
- **A column added to an existing table must be nullable or have a default,** or the migration is a compile error: existing rows need a value.
- `dropColumn`, `dropTable` and narrowing a type are destructive, so the migration must carry `@Breaking("reason")`, as [19-persistence.md](../19-persistence.md) requires.

### The `schema.lock` file

`schema.lock` is TOML, generated and committed. It records the schema the migrations produce, so `k check` can compare it with the entities without a database:

```toml
# Generated by `k migrate`. Do not edit by hand.
migrations = ["0001_create_accounts_and_notes", "0002_add_note_pinning"]

[tables.note]
entity = "notes.Note"
columns = [
    { name = "id", type = "uuid", primaryKey = true },
    { name = "owner_id", type = "text", indexed = true },
    { name = "is_pinned", type = "boolean", default = false },
]
```

- `k check` fails when **the entities differ from the lock** ("run `k migrate new`"), or when **replaying `migrations/` doesn't produce the lock** (a hand-edited lock or migration).
- Tables managed by the stdlib itself, such as `k.auth`'s session table, are not recorded. The stdlib migrates them.

## Why

- Strings in migrations and checked replay together give both stability and safety: history never changes meaning, and mistakes are still caught at compile time.
- A builder instead of raw SQL keeps migrations portable between SQLite in development and Postgres in production ([19-persistence.md](../19-persistence.md)).
- A TOML lock is diffable in review, so a schema change is visible in the pull request that makes it.

## Open questions

- Online migrations for large tables (backfilling a column in batches) need a way to run data steps outside the schema transaction.
- Whether `k migrate new` should detect renames, or always generate a drop and an add that the developer edits into `renameColumn`.
