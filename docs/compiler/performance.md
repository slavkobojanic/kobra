[testing.md §9](testing.md#9-benchmarks-and-performance-budgets). Sections 1–9 cover the syntax layer
(lexer, parser, tree sink); [§10](#10-semantic-analysis) covers semantic analysis (`k check`).

## 1. Running

```sh
scripts/bench-check.sh                                # pass/fail against the budgets (release build)
scripts/bench-check.sh --criterion                    # the same, then every criterion benchmark
cargo bench -p k_syntax                               # criterion only
cargo bench -p k_syntax -- '^parse/'                  # one group (regex filter on benchmark ids)
cargo bench -p k_syntax -- --save-baseline main       # record a baseline
cargo bench -p k_syntax -- --baseline main            # compare a change against it
K_BUDGET_SCALE=0.5 scripts/bench-check.sh             # slower machine: enforce half the throughput
scripts/bench-check.sh --sema                         # only the semantic budgets (--syntax: only syntax)
cargo bench -p k_sema                                 # semantic criterion benchmarks
cargo bench -p k_sema -- '^warm_body/'                # one group
```

`scripts/bench-check.sh` runs the `#[ignore]`d tests of `crates/k_syntax/tests/perf_budget.rs` with
`--release --test-threads=1 --nocapture` and exits non-zero when a budget is missed. It refuses to run in a
debug build. `K_BUDGET_SCALE` (in `(0, 1]`, default 1) scales throughput budgets down and time budgets
up for slower hardware such as shared CI runners; it never scales the linearity checks, which do not
depend on the machine.

**Profiling.** On macOS, Instruments' Time Profiler needs no extra tools or root:

```sh
cargo bench -p k_syntax --no-run                      # builds target/release/deps/syntax-<hash>
xctrace record --template 'Time Profiler' --output parse.trace --launch -- \
    target/release/deps/syntax-<hash> --bench --profile-time 8 '^parse/realistic/100k$'
xctrace export --input parse.trace \
    --xpath '/trace-toc/run[@number="1"]/data/table[@schema="time-profile"]' > parse.xml
```

`--profile-time` makes criterion run the routine for that long without analysis. The bench profile keeps
debug info (`[profile.bench] debug = true`), so frames are symbolicated, including inlined ones. On Linux,
`cargo flamegraph --bench syntax -- --bench --profile-time 8 '^parse/'` does the same.

## 2. Inputs

All benchmark input is generated by `crates/k_syntax/benches/workload/mod.rs`, which the benchmarks and
the budget check share through `#[path]` includes. The generator is a pure function of a size and a seed
(SplitMix64, seed `workload::SEED`), so every run measures byte-identical text. Its output is tested in
`crates/k_syntax/tests/workload.rs`, part of the normal test suite.

**Realistic input** (`workload::realistic(lines, seed)`): valid K that starts with an import block and
cycles through every declaration kind in a seeded order: components (props, injected services, state,
derived values, functions, a view with elements, modifiers, `if`/`for ... key`/`match`, and a style block
with rules, nested rules, pseudo-classes and elements, combinators, attribute selectors and `@media`),
pages (`requires`, `at` with route parameters, `loading`, `failed`, `metadata`), layouts, services (async
throwing functions, RPC implementations), protocols, entities, repositories, structs (generics, `where`,
`init`, computed properties), enums (payload cases, `match self`), classes, interfaces, extensions, themes
(tokens, variants), apps (`use` bindings), test suites (`expect`, `expect throws`) and top-level functions
and constants. Function bodies mix every statement kind; expressions mix every literal kind (integers in
every base, floats, units, colors), strings with escapes, interpolations and non-ASCII text, member and
optional chains, calls with labels and trailing lambdas, typed lambdas, lists, maps, tuples, ranges,
`??`, prefix operators and `try`/`await`. Doc, line and nested block comments appear throughout.

The tests guarantee that it parses with **zero diagnostics** for 64 seeds and at 1k and 10k lines (so the
benchmarks never measure error recovery by accident), that it produces every declaration, member,
statement, expression and style node kind and every literal and trivia token kind, that the line count is
as requested, and that lines average 22 to 48 bytes (the measured average is 38 bytes per line and 2.95
bytes per token; the project-size budgets assume about 35 bytes per line).

`workload::typical_file(seed)` is realistic input of 300 lines: the unit of the "typical 300-line file"
budget. The budget check measures eight of them (different seeds) and enforces the slowest.

**Pathological input** (`workload::Pathological`): fifteen families, each stressing one dimension, each
generated at a requested size (`megabyte_size()` gives about 1 MB):

| Family | Shape | Valid |
|---|---|---|
| `deep-parens` | lines of `let a = ((( ... x ... )))` nested 300 deep (the limit is 400) | yes |
| `too-deep` | one expression nested 500,000 deep: K0134 once, the excess skipped iteratively | no |
| `deep-blocks` | functions with `if` blocks nested 150 deep | yes |
| `deep-view` | components whose views nest elements 150 deep, each with a modifier | yes |
| `deep-style` | components whose style blocks nest rules 150 deep | yes |
| `long-line` | one 1 MB line: a list literal with 160,000 elements | yes |
| `long-string` | one 1 MB string literal | yes |
| `huge-interpolation` | one string with 120,000 interpolations | yes |
| `nested-interpolation` | strings nested in interpolations 100 deep, one per line | yes |
| `many-diagnostics` | 40,000 lines, each with one or more lexer or parser errors (most with quick fixes) | no |
| `long-broken-line` | one line of 32,000 broken fragments (`!`, `&&`, `;`, stray closers) | no |
| `comment-heavy` | line, doc and nested block comments | yes |
| `unicode-strings` | strings of CJK, Devanagari, Cyrillic, accented and emoji text | yes |
| `member-chain` | `x.m.m.m...` with 500,000 links (a 500,000-deep tree built by a loop) | yes |
| `long-sum` | `x + x + ...` with 250,000 terms (a 250,000-deep tree) | yes |

## 3. Method

**Budget check** (`perf_budget.rs`). Each measurement runs the operation twice to warm up, then repeats it
until it has run both a minimum number of times and for at least 300 ms, and keeps the **fastest** run.
Interference (other processes, efficiency cores, interrupts) only ever makes a run slower, so the minimum
is the most stable estimate of the code's own speed and keeps the check from flaking on a busy machine.
The result of each run is dropped outside the timed region: the budget is about producing the tree.
Throughput is in decimal megabytes (10^6 bytes) per second, the unit of the budget table.

| Check | Requirement | Source |
|---|---|---|
| lexing realistic input, 100k lines (3.81 MB) | ≥ 150 MB/s | architecture.md §12 |
| lexing + parsing realistic input, 100k lines | ≥ 25 MB/s | architecture.md §12 |
| the slowest of eight typical 300-line files | ≤ 0.5 ms | architecture.md §12 |
| lexing + parsing every pathological family at about 1 MB | ≥ 10 MB/s | architecture.md §12, below |
| realistic input, 10k → 100k lines | time ratio ≤ 14 (linear is 10) | architecture.md §4.2 "Linearity" |
| every pathological family, size s → 4s | time ratio ≤ 6 (linear is 4; quadratic would be 16) | architecture.md §4.2 "Linearity" |

**The pathological floor** (≥ 10 MB/s, added to architecture.md §12 with this document). The "Linearity"
guarantee of architecture.md §4.2 says nothing about the constant; the floor does. 10 MB/s means a
megabyte of the worst shape we know still parses in 100 ms, so a hostile or generated file cannot stall
the editor or `k check`, and it is 40% of the general parse budget, so a regression in recursion, error
recovery, quick-fix computation or deep-tree teardown is caught even when realistic input is unaffected.
The slowest family today (`deep-parens`, about 19.5 MB/s, where every byte is a token and every token a
level of nesting) has roughly 2x headroom.

**Criterion benchmarks** (`benches/syntax.rs`) report the mean with a confidence interval and are meant for
comparing a change against a saved baseline. Each benchmark reports both lines/s ("elem/s") and bytes/s
(criterion prints binary MiB/s). Unlike the budget check, the timed region includes dropping the result,
so trees deeper than 256 levels pay for their iterative teardown here.

**Noise.** The baseline machine has 10 performance and 4 efficiency cores and was running other work.
Criterion runs on whichever core the scheduler picks; a run that lands on an efficiency core can be twice
as slow (one `typical_file/lex` run measured 90 µs instead of 38 µs). Re-run a surprising result in
isolation before acting on it, and prefer the budget check's best-of numbers for absolute statements.

(`deep-parens`, `member-chain`, `many-diagnostics`) lex at 155–180 MB/s, realistic code (2.95 bytes per
token) at about 250 MB/s, and long tokens (strings, comments, indentation) at over 1 GB/s. The lexing
budget is enforced on realistic input only; the one-byte-token families are close to 150 MB/s and are
watched through the pathological floor on lexing + parsing.

## 6. Profile of a parse

Time Profiler, `parse/realistic/100k` (lexing, parsing, tree building and dropping the tree), 8,117
samples at 1 ms, before the changes of [§7](#7-changes-made-while-setting-up-the-benchmarks). Inclusive
shares of the whole iteration:

| Phase | Share | Notes |
|---|---|---|
| Lexer (`lex`) | 20% | trivia, identifiers and keyword matching dominate; no allocation per token |
| `Parser::new` (trivia-free token view) | 6% | one pass over all tokens, four pushes per significant token |
| Grammar functions (`source_file` and below) | 12% | recursive descent and the Pratt loop |
| Tree sink (`sink::build`) | 42% | see below |
| Dropping the tree | 16% | rowan frees every node and decrements every token's reference count |
| Other (diagnostic sorting, criterion) | 4% | |

Inside the sink: token interning 21% (of which hash-map lookups 13%: hashing 5.5%, key comparison 5.3%),
building green nodes (`GreenNode::new`, one allocation per node) 11%, walking events and trivia 10%.

So more than half of a parse is spent producing and freeing rowan's green tree, and only about a third
in the lexer and the grammar. Speeding up the grammar functions alone cannot move the parse number much;
the levers are in the sink and in tree memory management ([§8](#8-known-costs-and-next-steps)).

## 7. Changes made while setting up the benchmarks

Every budget was already met by the code as written; the profile still showed three cheap wins, which were
made with all tests (unit, golden corpus, property, robustness) green. Effects are criterion means on the
benchmarks above.

1. **Per-kind token slots in the sink** (`parser/sink.rs`, `TokenCache`). Keywords and punctuation (whose
   text is fixed by their kind) are served from one slot per kind, a `"\n"` newline and runs of up to 32
   spaces from slots by length; only identifiers, literals, comments and other trivia go through the hash
   map. On realistic input the slots serve 77% of all tokens. A token whose kind equals the lexer's kind
   uses the slot without comparing texts (the lexer guarantees that a fixed-text kind has exactly its
   text; the property tests and fuzzers check it, and debug builds assert it); a remapped contextual
   keyword is compared first.
2. **Word-at-a-time hashing** (`FxHasher::write`): eight bytes per mixing step instead of one, for the
   tokens that still go through the map.
3. **No temporary vector per node in deep-tree teardown** (`syntax.rs`, `Drop for Parse`): the iterative
   teardown of trees deeper than 256 levels collected every node's children into a fresh `Vec`; it now
   extends its work list directly.

Plus a tighter loop in `Parser::new` (iterating token kinds with `starts.windows(2)` instead of two
bounds-checked lookups per token).

Effects: `typical_file/parse` −9%, `parse/realistic/*` −5% to −7%, `parse_only/realistic/10k` −9%, deep
trees −22% to −29% (`deep-parens`, `member-chain`, `long-sum`), `long-broken-line` −14%, `comment-heavy`
−12%, `unicode-strings` −12%.

## 8. Known costs and next steps

None of these is needed to meet a current budget; they are listed in order of expected gain so the next
person to work on parser speed can start from data.

1. **Tree teardown** (16% of a realistic parse, more for deep trees). Dropping a green tree touches every
   node and every token reference. The parse result is usually kept (by the query engine) rather than
   dropped, so this matters most for one-shot tools. Options: keep the previous file version's tree alive
   so freeing happens off the critical path, or free on a background thread.
2. **Green node allocation** (11%). One heap allocation per node through the global allocator. rowan does
   not support arenas; a faster allocator (mimalloc) would help across the whole compiler and is the first
   thing to measure when k_sema exists.
3. **Interning identifiers** (the remaining map traffic, about 22% of tokens). Hashing could reuse a hash
   computed by the lexer, which already scans the identifier; or identifiers could be interned once in a
   compiler-wide name table that the sink and semantic analysis share.
4. **Events.** `sink::build` moves each event out with `mem::replace`; a sink that consumes the event
   vector by value and resolves `forward_parent` chains in a pre-pass would avoid the writes.
5. **Lexer.** Whitespace and identifier runs are scanned a byte at a time. A word-at-a-time scan for runs
   of spaces and for identifier characters would mostly help indentation-heavy code. The lexer has 1.6x
   headroom on its budget and is not a priority.
6. **Parallelism.** Files are independent, and architecture.md §12 plans parallel parsing, so for whole
   projects the single-core numbers here scale with the number of cores.

## 10. Semantic analysis

### 10.1 Running

`scripts/bench-check.sh` (or `--sema`) runs the ignored tests of `crates/k_sema/tests/perf_budget.rs`:
first every timing check with `--test-threads=1`, then the memory check alone in its own process, so no
other test's freed memory is counted. `cargo bench -p k_sema` runs `crates/k_sema/benches/sema.rs`.
Profiling works as in [§1](#1-running), with the `sema-<hash>` bench binary and an id filter such as
`'^warm_body/realistic/100k$'`.

### 10.2 Inputs

`crates/k_sema/benches/project/mod.rs` generates projects as `(path, text)` lists, a pure function of size
and seed (SplitMix64, `project::SEED`). `crates/k_sema/tests/project_workload.rs` (normal test suite)
guarantees that every generated project, every family and every benchmark edit analyses with **zero
diagnostics**, so no benchmark measures error paths.

**Realistic** (`project::realistic(lines, seed)`): `k.toml`, `App.k`, a theme, a `core` module of
generic types (`Pair<A, B>`, `Batch<T>`, `Outcome<T>`, an interface with a default method, a generic
function), then feature modules until the line count is reached exactly (the last module gets
top-level helpers to make up the rest). A feature module has a `Codable`/`Equatable` record implementing
two interfaces, a status enum with payload cases and guarded, exhaustive `match`es, an error enum with
`rpcFailure`, an interface, a protocol with typed-`throws` rpcs, the server service implementing it, a
client service (`@Inject` of the protocol and of the previous module's service, `@State`, `@Derived`,
10–24 methods mixing loops, `guard`, lambdas, generic calls, `match` and optionals), a component (props,
state, a view with `if`/`match`, modifiers, a style block with `@media`), a page (`@Inject`, `@Load`,
`loading`, `failed`, metadata, a keyed `for`) and a test suite. Each module imports its predecessor
and `core`. At 100k lines: **1,369 files, 3.12 MB** (31 bytes per line; architecture.md §12 assumes
about 1,000 files and 3.5 MB), 136 feature modules.

**Edits.** `project::body_edit` changes one literal in the body of a private helper of feature 0's
service (the same line count, one changed line, a test checks it); `project::signature_edit` adds a public
method to that service. The warm checks alternate between two versions so every run is a real change.

**Pathological** (`project::Pathological`, default sizes in parentheses):

| Family | Shape |
|---|---|
| `deep-generics` (48) | `Wrap<Wrap<…<Int>>>` nested *size* deep in 40 functions: annotated and inferred nested constructor calls, a generic `map` on the result |
| `huge-match` (2,000) | an enum of *size* cases (every third with a payload), two exhaustive `match self`, eight guarded `match`es with `default` |
| `import-chain` (1,000) | *size* modules, each importing the previous module's struct and injecting its service |
| `wide-di` (1,000) | one service injecting *size* services, each injecting a shared leaf; a page injecting the root |

### 10.3 Method

As in [§3](#3-method): best of repeated runs, results dropped outside the timed region. A **cold check**
is `AnalysisHost::with_files` plus `diagnostics()` (parsing included); the embedded stdlib, parsed once
per process, is warmed first. A **warm re-check** is `apply_change` of one file plus `diagnostics()` on
a host that has already answered. **Memory** is the process's resident set (`/proc/self/status` on
Linux, `ps -o rss=` elsewhere; the crate forbids `unsafe`) with a warm host after four edits and a live
snapshot. "8 threads" is `Options::with_threads(8)` (or every core if fewer); the semantic pass itself is
single-threaded today, so only parsing uses them.

| Check | Requirement | Source |
|---|---|---|
| cold check, 100k lines, 8 threads | ≤ 1.0 s | architecture.md §12 |
| cold check, 100k lines, 1 thread | ≤ 4.0 s | architecture.md §12 |
| warm re-check after a body edit, 100k lines | ≤ 30 ms | architecture.md §12 |
| warm re-check after a signature edit, 100k lines | ≤ 150 ms | architecture.md §12 |
| resident memory, warm 100k-line project | ≤ 1.5 GB | architecture.md §12 |
| realistic 10k → 100k lines | time ratio ≤ 14 | sema.md §15 (no quadratic algorithms) |
| pathological families, size s → 4s | time ratio ≤ 6 | sema.md §15 |
| `deep-generics`, depth d → 4d | time ratio ≤ 20 | below |

The `deep-generics` bound is quadratic, not linear, by necessity: the checker records the type of every
expression (`type_at`), and in a chain nested `d` deep the expression at level `k` has a type of size `k`,
so materializing them is Θ(d²) whatever the algorithm (quadratic is x16). The bound still catches the
cubic behaviour it had before [§10.6](#106-changes-made-while-setting-up-the-benchmarks) (x44).

| `wide-di` 1,000 → 4,000 services | x4.19 | ≤ x6 | met |

No budget was changed. **Every budget is met.** Before round 2 the warm body edit took 101.6 ms (3.4x
over): `check::analyze` rebuilt the `Program` and re-checked every declaration on every revision, and
checking bodies was 73% of a re-check. Round 2 keeps each file's **body facts** (diagnostics, types,
resolutions and the side facts the project passes read) and replays them for every file whose text is
unchanged, as long as no signature in the project changed (`crate::warm`; sema.md §3.3 and §16). Every
signature is resolved eagerly before the bodies (about 6 ms at 100k lines), which makes the signature
facts independent of which body first needs them. A warm body edit now costs, at 100k lines:

| Phase | ≈ ms |
|---|---|
| rebuilding the `Program` | 9 |
| eager signatures, project checks, imports | 7 |
| checking the edited file's bodies, replaying the other 1,368 files' facts | 1–2 |
| routing, RPC, app, DI, client references, unused imports and classes | 7.5 |
| parsing the edited file, name table, host overhead | 1–2 |

The headroom is small. The next steps, in order of payoff: keep the `Program`'s item tree across
revisions (it depends only on signatures, so an unchanged signature set could reuse it); make the
project passes incremental (most read only signatures plus a few body facts); then parallelize the body
phase, which needs `Send` syntax pointers (§3.5). A signature edit still re-checks everything; per
declaration dependency tracking (early cutoff below the file level) would cut it.

**Exhaustiveness.** A `match` whose arms share one constructor (`case .c(1)`, `case .c(2)`, …) used to be
quadratic in the arms (20k arms: 12.7 s); `pattern::Rows` now indexes rows column after column, and
20k such arms take 0.04 s (sema.md §15).

### 10.6 Changes made while setting up the benchmarks

Measured with the budget check before → after; all tests (unit, corpus, examples, robustness, property)
green after each change.

1. **Exhaustiveness linear in the number of cases** (`pattern.rs`). `arity` enumerated every case of the
   enum (with its signature) to find one constructor's fields, the wildcard rule checked coverage with
   a linear `contains` per constructor and re-scanned all rows per constructor, and every arm was tested
   against every earlier row. Now a constructor's fields come from its own signature, the wildcard rule
   groups rows by head constructor once, and `pattern::Rows` indexes a growing matrix by head
   constructor (used by `match` and `catch`). `huge-match`: 686 ms → 34 ms; 2,000 → 8,000 cases went
   from x16.2 (quadratic) to x4.2. Tests: `tests/project_workload.rs`, wide-`match` cases (exhaustive,
   one case missing at several positions, repeated arms, guards, `default`).
2. **Shallow resolution in `unify` and `assignable`** (`body.rs`), and a `resolve` that allocates
   only when a type contains a bound variable. Both resolved both types deeply at every level of the
   recursion, which is quadratic per call and cubic over a nested constructor chain. `deep-generics`
   at depth 48: 50.7 ms → 11.9 ms; 48 → 192 went from x44.7 to x10.2.
3. **Types for `type_at` rendered on demand** (`ty::NameTable`, `check::SemaResult`). Every
   expression's type was rendered to a `String` (with a `format!` per nominal type) whether or not anyone
   asked; they are now kept as `Ty` and rendered by `Analysis::type_at` from a per-revision name table.
4. **Fx hashing** (`fx.rs`) for the `Cx` memo tables, the recorded types and resolutions and the
   `Program`'s name maps: SipHash was about 10% of a check.
5. **Lazy identifier scan for unused imports** (`check::unused_imports`): the per-file identifier set
   is only built when an import isn't used by any checked body (10% of a warm re-check before).
6. `Program::write_decl_name` appends a qualified name without a temporary `String`.

Effect on the 100k-line project (budget check, best-of): cold on 1 thread 141 → 120 ms, on 8 threads
125 → 102 ms, warm body edit 125 → 102 ms.

### 10.7 Next steps

1. **Early cutoff** (the warm budget): per-declaration memoization of body results (diagnostics, types,
   resolutions, and the facts project-wide checks read: used imports, references, DI uses), keyed by
   the declaration's syntax and the signatures it read, as sema.md §3.3 designs. Needs `Program` and
   signatures that survive a revision (stable `DeclId`s, sema.md §3.4).
2. **Parallel checking** of declarations (sema.md §3.5): `Cx` uses `RefCell`/`Rc` and rowan nodes, which
   are not `Send`; per-declaration results with `Send` syntax pointers come with item 1.
3. **Stdlib computed once per process**: about 2.5 ms per check.
4. **Deep types**: hash-consed `Ty`s (sema.md §3.4) would make resolving recorded types linear in the
   number of distinct types rather than their total size.
